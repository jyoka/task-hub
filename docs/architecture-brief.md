# Architecture Brief(7 つの関門)

新しいプロダクトや project を作るとき、AI は画面や HTML からいきなり作りはじめがちです。動く画面はすぐにできますが、
落ちたら誰が気づくのか、API key をどこに置くのか、といったことは決まらないまま残ります。
task-hub では、作業先リポジトリに **Architecture Brief**(`docs/architecture.md`)を置き、アーキテクチャの
7 つの関門を一通り考えたことを記録に残します。

全部を作る必要はありません。関門ごとに「今どうするか」か「今はやらない理由と、いつ必要になるか」を書きます。
POC でも、作らないことを自覚して決めている状態にするのが目的です。

Brief は 2 か所で使います。

| 場所 | すること |
|---|---|
| `/chief`([skills/chief/SKILL.md](../skills/chief/SKILL.md)) | 新しいプロダクトの話が出たとき、または作業先リポジトリに `docs/architecture.md` がないとき、カードに分ける前に Brief の下書きを作ってユーザーに確かめる |
| `task check` の Architect([worker/READINESS.md](../worker/READINESS.md)) | カードの変更が関門に触れていて、Brief と食い違うか Brief にないときに指摘する([下記](#task-check-の-architect)) |

## 7 つの関門

| # | 関門 | 決めること |
|---|---|---|
| 0 | 基盤リソース | ネットワーク、サーバー、ストレージ、DB、権限。データが消えたらどうなるか |
| 1 | IaC | リソースをコードで書くか(Terraform、OpenTofu、PaaS の設定ファイルなど) |
| 2 | パッケージング | コンテナにするか。イメージをどこに置くか |
| 3 | 実行と編成 | どこで動くか。落ちたら誰が再起動するか。スケール、冗長化とフェイルオーバー |
| 4 | CI/CD | テスト、ビルド、デプロイの自動化。戻し方 |
| 5 | 設定と秘密情報 | API key などをどこに置き、どう注入するか。漏れたときの差し替え |
| 6 | 可観測性 | ログ、メトリクス、トレース、アラート。ダウンしたときの対応 |

## 規模の段階と最低要件

段階は 3 つです。Brief の先頭に、今どの段階かを書きます。

| 段階 | 目安 |
|---|---|
| POC | 作った人と、試してもらう数人だけが使う。止まっても誰も困らない |
| ベータ | 実ユーザーがいる。止まると困る人がいるが、約束(SLA)はない |
| 本番 | SLA がある。止まる時間や失うデータの上限を約束している |

段階ごとに、各関門で最低限求めることです。右の 2 列は路線の候補です。

| 関門 | POC | ベータ | 本番 | 無料・オープンソースの路線 | マネージド有料の路線 |
|---|---|---|---|---|---|
| 0. 基盤リソース | 使うリソースを一覧にする。データが消えてよいかを 1 行で書く | バックアップを取り、復元を 1 回試す。権限を最小にする | 環境(検証と本番)を分ける。バックアップの保持と復元にかかる時間の目標を決める。権限を役割ごとに分ける | VPS + PostgreSQL / SQLite、MinIO | マネージド DB(Render Postgres、Supabase、Cloud SQL、RDS)、S3 |
| 1. IaC | 今はやらない、で可。手で作ったものを Brief に書き出す | 設定ファイルかスクリプトで、同じ環境をもう一度作れる | 全リソースをコードにし、変更は PR でレビューする(plan を PR で見る) | OpenTofu、Ansible、docker-compose.yml | HCP Terraform、Pulumi Cloud、PaaS の設定ファイル(Render の Blueprint など) |
| 2. パッケージング | PaaS のビルドに任せてよい。依存の版を lockfile で固定する | Dockerfile でイメージを作り、コミットでタグをつける | 同じイメージを検証から本番へ流す。イメージの置き場所、保持、脆弱性の検査を決める | Docker / Podman、GitHub Container Registry、Harbor | Docker Hub の有料プラン、ECR、Artifact Registry |
| 3. 実行と編成 | 単一インスタンスで可。落ちたときの影響と復旧手順を 1 行で書く | 自動で再起動する。ヘルスチェックを置く。メモリの上限と、超えたときの動きを決める | 複数台、ヘルスチェック、自動フェイルオーバー。スケールの条件を決める | Docker Compose(`restart:`)、Coolify、systemd、k3s | Render や Fly.io の上位プラン、Cloud Run、マネージド K8s(GKE、EKS) |
| 4. CI/CD | テストとデプロイの手順を 1 行ずつ書く | PR ごとにテストを動かす。main からのデプロイを自動か 1 コマンドにする | テストが通らないとデプロイしない。戻す手順を決め、1 回試す | GitHub Actions(無料枠)、Woodpecker CI | GitHub Actions の有料分、CircleCI、PaaS の自動デプロイ |
| 5. 設定と秘密情報 | 秘密情報をリポジトリに入れない。どこに置いたかを書く | 環境ごとの置き場所を決める。漏れたときの差し替え手順を書く | 保管庫から注入する。誰が読めるかを決め、定期的に差し替える | SOPS + age、Infisical(自前で動かす)、`.env` | Doppler、1Password Secrets Automation、AWS Secrets Manager、PaaS の環境変数 |
| 6. 可観測性 | ログを見る場所を書く。ダウンに気づく方法を書く(なければ「気づけない」と書く) | 外形監視とアラートの送り先を決める。エラーを記録する。メモリと CPU を見る | メトリクス、トレース、アラート。ダウンしたときの手順(runbook)と、誰が対応するかを決める | Prometheus / Grafana、Loki、Uptime Kuma、OpenTelemetry | Datadog、Grafana Cloud、Sentry、Better Stack |

- 候補は例です。ここにない路線を選んでも構いません。
- 料金は変わります。月額の目安は、Brief を書くときに各サービスの料金ページで確かめます。この文書には金額を書きません。
- マネージドに払うのは、機能のためではなく運用を任せるためです。無料・オープンソースの路線でも、たいていの機能は手に入ります。
  払うなら、何の運用を任せたいのか(夜中の再起動、バックアップ、更新、監視の維持など)を Brief に書きます。

## Brief のテンプレート

作業先リポジトリの `docs/architecture.md` に、次の形で置きます。関門ごとに 4 項目を必ず埋めます。
今はやらない関門は、「決定」に「今はやらない」と書き、理由と見直すきっかけを書きます。

```markdown
# Architecture Brief

- 段階: POC / ベータ / 本番 のどれか
- 更新: YYYY-MM-DD

## 0. 基盤リソース

- 決定: (今の決定、または「今はやらない」)
- 理由:
- 見直すきっかけ: (例: 「ユーザーが 100 人を超えたら」)
- 路線とコスト: (無料・オープンソース / マネージド有料 のどちらか。選んだもの、理由、月額の目安。有料なら払う理由)

## 1. IaC

- 決定:
- 理由:
- 見直すきっかけ:
- 路線とコスト:

## 2. パッケージング

- 決定:
- 理由:
- 見直すきっかけ:
- 路線とコスト:

## 3. 実行と編成

- 決定:
- 理由:
- 見直すきっかけ: (例: 「メモリ不足が 1 回でも起きたら」)
- 路線とコスト:

## 4. CI/CD

- 決定:
- 理由:
- 見直すきっかけ:
- 路線とコスト:

## 5. 設定と秘密情報

- 決定:
- 理由:
- 見直すきっかけ:
```

書いた例です(POC の Web サービス 1 つ、関門 3 だけ)。

```markdown
## 3. 実行と編成

- 決定: Render の Web サービス 1 台(numInstances: 1)。落ちたら Render が再起動する。メモリ不足で落ちると、
  再起動までの数分、話している途中の会話が切れる。復旧はダッシュボードの Manual Deploy
- 理由: 使うのは試してもらう 5 人だけで、止まっても困る人がいない
- 見直すきっかけ: 実ユーザーに公開するとき。メモリ不足で落ちたことが 1 回でもあったら
- 路線とコスト: マネージド有料(Render の Starter)。月額は料金ページで確かめた額を書く。払う理由: サーバーの更新と再起動を任せたい
```

## task check の Architect

`task check` の敵対的レビューには、Architect の視点があります([worker/READINESS.md](../worker/READINESS.md))。
Architect は、カードの Goal と作業先リポジトリの `docs/architecture.md` を読み、カードの変更が関門に触れているかを見ます。

関門に触れる変更の例です。

- 新しいサービスやデータストアを足す
- 秘密情報(API key など)を足す、置き場所を変える
- デプロイ先、プラン、台数を変える
- 常駐プロセスやバックグラウンドのワーカーを足す。メモリや CPU を大きく使う処理を足す

触れていない変更(画面の文言、小さな UI の修正など)には、Brief がなくても何も言いません。
触れているときの扱いです。

| 場合 | 扱い |
|---|---|
| 段階が本番なのに、関門 3、5、6 のどれかに決定がない(空か「今はやらない」) | blocking |
| `docs/architecture.md` がない | minor |
| 変更が Brief の決定と食い違う、または Brief に書かれていない関門に触れる | minor |
| 有料のマネージドサービスを新しく増やすのに、Brief に払う理由がない | minor |

blocking は 1 つだけです。ほかは、エージェントがそのまま作っても困らないので minor にしています。
minor の指摘は判定を NO-GO にしません。Brief を書くカードを別に作るかどうかは、人が決めます。

Goldfish は作業先リポジトリの外を読みません。そのため、関門と最低要件の要点は READINESS.md の Architect の中にも書いてあります。
この文書を変えたら、READINESS.md の Architect も合わせます。
