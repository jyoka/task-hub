# task-hub の開発から得た教訓 (2026-09-23 から 2026-09-27)

task-hub を作り、本物で試して分かったことのうち、次の判断に使えるものだけを残しています。個々の不具合の直し方は
git の履歴と [design.md](design.md) にあります。直し終えて、ほかに活かせる教訓のない項目は消します。

## 経緯を 1 つの表で

| バージョン | 考え方 | 変更した理由 |
|---|---|---|
| 0.1 | クラウドのエージェント (Claude routines) がタスクを取得し、ボードの `main` にステータスを push する | 1 つのブランチに複数の書き手がいるため、ロックと競合への対処が必要でした。ユーザーはこれを混沌としていて危険だと評しました |
| 0.2 | ボードに書き込むのは Mac だけ。指示はトリガーに入れ、結果は PR で返ってくる | まだ Claude 専用でした。ユーザーは Codex と Pi も使い、仕事用の Mac では Kiro しか使えません |
| 0.3 | 任意のエージェント CLI を worktree 内でローカル実行し、タスクごとに herdr のワークスペースを 1 つ使う。エージェントはファイルを編集するだけ | 4 つのエージェントで実証できましたが、ボードは手元の markdown で、かんばん画面がありませんでした |
| 0.4 | ボードを GitHub Project に移す。タスクは非公開リポジトリの Issue、カードを Ready に移すと Mac の `task watch` が始める | 現在の設計です(かんばん画面は自分で作らず GitHub Project を使う。どこからでも、どのエージェントからでも使えるため) |
| 0.5 | カードの Base branch 欄で、main 以外の作業中のブランチから始める。GitHub への問い合わせを軽くする | ユーザーはほとんどの作業で先にブランチを切るため |
| 0.6 | PR の前の自動レビューと 1 回の差し戻し、Blocked の仕分け、`[env]` と `[setup]`、総指揮の `/chief`、タスクの前後関係 | 人のレビューがボトルネックで、評価と Replan と順番の管理を人だけが担っていたため |

作り直しは低コストで済みました。ボードの形式と PR の約束事がそのまま残ったからです。ただし、どの作り直しも、
最初に 1 つ質問していれば見えていたはずの制約が原因でした。

## AI エージェントの作業効率

### うまくいったこと

- **エージェントとの約束事はできるだけ小さくします。** 「ファイルを編集し、テストを実行し、`.task-report.md` を書く」
  だけにして、git と GitHub の作業をすべて task-hub に移すと、4 つのベンダーの挙動がそろい、Codex のサンドボックス
  (ネットワークなし、フォルダ外への書き込み不可)も回避できました。
- **出力形式はプロンプトではなくコードで保証します。** PR の説明は task-hub がレポートファイルから組み立てます。
- **"Please review" を明示的に求めます。** どのエージェントも、ファイル、判断、リスクの具体的な一覧を出しました。
- **ブロックという逃げ道があると、エージェントは正直になります。** 知りようのないパスワードを求めるタスクで、Claude は
  捏造を拒み、理由と安全な選択肢を示しました。行き詰まることも正当な結果だと指示に書いていたからです。
- **並行作業は人間がレビューできる量 (3) に抑えます。** 簡単なタスクは 15 から 55 秒で終わり(Codex が最も遅く、
  出力も冗長)、レビューの方が時間がかかります。

### 無駄になった労力

- **制約に気づくのが遅れたこと。** どのエージェントか、どのマシンか、どの端末ツールか(tmux ではなく herdr)、どの
  git ホストか。答えが遅れるたびに設計をやり直しました。設計の前に確認します。
- **エージェントが疑問に思いそうなことは、指示で答えておきます。** レポートファイルはコミットされない、git の index は
  関係ない(task-hub は作業ツリーをコミットする)。どちらも 1 文足すまで、エージェントは的外れな対応を繰り返しました
  (後者は差し戻しが収束しなかった jyoka/tasks#43)。
- **長いコマンドは、エージェントではなくツールがバックグラウンドに回します。** tasks#47 で、10 分を超えた
  全体テストを Claude Code の Bash ツールが自動でバックグラウンドに回し、非対話の `claude -p` はその終わりを待たずに
  終わりました。レポートがないので Blocked です(2026-10-01)。エージェントが自分で回したのではないので「バックグラウンドで
  実行しない」では防げず、指示書に「小さく分けてそれぞれ待つ」「動いている間に終えない」「走らせた範囲を Report に
  書く」を足しました。テストは育つので、いつかどのエージェントでも時間の上限に届きます。
  ところが tasks#51 では、Goal にも同じことを書いたのに、エージェントはテストをバックグラウンドで走らせて
  同じように終わりました。**文面では防げなかったので**、組み込みの `claude` のコマンドに環境変数を付け、仕組みとして
  止めました(`CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` でバックグラウンド実行をなくし、`BASH_DEFAULT_TIMEOUT_MS` と
  `BASH_MAX_TIMEOUT_MS` で前景を 30 分まで待てるようにする)。指示で頼むより、道具の側で選べなくするほうが確かです。
- **前景で待てる時間と、テストを待ってよい時間は別です。** tasks#170 は PTY のテストの後片付けで
  `waitpid` が止まり、worker が 20 分以上待ちました。単体の再実行でも同じ場所で止まりました。
  worker と reviewer の指示に、有限の期限、長い実行の進捗確認、止めるプロセスの所有確認、原因を直す前の
  同じ再実行の禁止を足しました。テストの本体だけでなく後片付けにも期限を付けます。ログが静かなだけで
  ハングとは決めず、プロセスや更新時刻で確かめます。指示だけでは守られないことがあるので、のちに実行側にも
  watchdog を足しました(決定事項 19)。そこでも同じ考えで、出力がないだけでは止めず、CPU も使っていないときだけ止めます。
- **ヘルプの文面から CLI のフラグを推測しないこと。** `codex exec --full-auto` は Codex 0.155 に存在しませんでした。
  頼る前に一度実行し、昔からあるフラグを優先します。

## こうしたツールの作り方

- **フェイクを使った単体テストは、自分の思い込みを確かめるだけです。** 0.3 では 27 件、0.4 では 28 件のテストが
  通った状態から、本物で動かすたびに 4 から 7 個の不具合が出ました。フェイクは本物より寛容です(コミットのない PR を
  受け付ける、列の名前の綴りや予約語 `Repo` を気にしない、失敗の仕方が 1 通りしかない)。外部サービスに頼る部分は、
  名前、予約語、回数制限、すでにあるデータ(前のテストの `task/1` ブランチ)まで含めて、本物で一度通すまで完成と
  言いません。本物で見つけた失敗は、まずフェイクで再現してから直します。
- **呼ぶ回数ではなく、1 回の重さを測ります。** GraphQL は取り出す量で点数が決まり、`gh project item-list` は 1 回
  101 ポイントでした。回数を減らしても上限に届き、測って初めて原因が分かりました。今は必要な欄だけを取る問い合わせで
  1 回 1 ポイントです。欄を足すときも、足す前に `rateLimit { cost }` で測ります(前後関係の追加でも 1 ポイントのまま)。
  `gh api rate_limit` は上限に当たっている最中に「残り 5000」と表示したので、GraphQL の `rateLimit` を見ます。
- **わざと壊すテスト (ミューテーション) を行います。** 直した部分を戻すとテストが落ちるかを毎回確かめると、毎回
  テストの抜けが見つかりました(引用の照合、削除行、「今から読む」)。待つテストには必ず時間制限を付けます。一度、
  失敗せずに待ち続けるテストで、確認の途中の `bin/task` を壊したままにしかけました。
- **ときどき失敗するテストも、原因を再現してから直します。** 原因はフェイクの GitHub の書き方(空にしてから書く)で、
  並べて動かすと読み取りの大半が失敗しました。一時ファイルに書いて置き換えると 0 回です。
- **何かを変える前に、テストの分離を確認します。** `HERDR_SESSION` では herdr のコマンドが分離されず、ユーザーが使用中の
  セッションに workspace を作ってしまいました。どこに届くかを読み取り専用で確かめてから変更します。
- **人が使っているペインに、試験のために文字を送りません。** 入力欄に送信前の文字があると、それとつながって送信されます。
- **ユーザー個人の環境に依存しないこと。** SSH キーや git のプロトコルはマシンごとに違います。task-hub の clone に
  だけ `gh` のログインを使う HTTPS を設定すれば、どこでも動きます。
- **1 つのファイルに書き込むのは 1 者だけにします。** 競合はいつも、ロックではなく持ち主を決めることで直りました。
- **道具は、開発している clone から動かしません。** 開発中のブランチのまま本物のタスクが始まったことがあります。
- **GitHub の動きは、ドキュメントどおりとは限りません。** main 以外へのマージで `Closes` が Issue を閉じたり閉じなかったり
  し、作ったばかりのカードが一覧に 20 分以上出ないこともありました。当てにせず、task-hub の側で確かめます。
  Project のワークフローも、有効にするのは「Item closed」だけにします(ほかは task-hub の Status を上書きします)。

## 評価と Replan を自動化して分かったこと (0.6)

- **新しいコンテキストの同じモデルで、reviewer は十分に働きました。** 「敵対的に」と書くだけでなく、「受け入れ条件を
  1 つずつ根拠付きで」「場所と具体的な入力を書けない指摘は出さない」と確かめ方を指定すると、行番号やコマンドの出力を
  示し、自分でテストも実行しました。
- **指示で禁じても、守らせるのはコードです。** reviewer が編集して `git add` すると、その編集が PR に入る穴を自分で
  作っていました(アーキテクチャのレビューで発見し、再現してから直した)。今は起動前の状態を記録して戻します。
- **作る前に実績を数えました。** Blocked を仕分ける LLM を作る前に数えると、実作業の Blocked は 2 件で、どちらもコードで
  直すもの(`.env` がない、前提の PR が未マージ)でした。前者は `[env]` で、後者は前後関係(下記)で直りました。
  replanner はコメントだけの小さな形で始めています。
- **本物のモデルは、根拠の形式を守れました。** replanner の `answered` に求める `path:行番号` と完全一致の引用を出し、
  task-hub がそれを実物と照らし合わせます。
- **外からのレビューは、主張を確かめてから優先順位を付けます。** 実害が確かだった指摘は、レビュー自身の推奨とは
  順番が逆でした。
- **調べものは「変更なし」でも成果です。ただし推測せず、ラベルで明示しました。** 普通のタスクの「変更なし」は失敗の
  しるしなので、区別はエージェントの出力ではなく Issue の `research` ラベルで付けます。
- **決める前に測ります(仮想環境)。** worktree ごとの仮想環境は pip では 21 秒・554MB でしたが、uv は APFS の複製で
  2 回目から 0.3 秒・5MB でした。これで「リポジトリごとの準備コマンド `[setup]`」に決まりました。

## 総指揮とタブ (0.6)

- **プロンプトで道具の選び方は縛れませんでした。** `/chief` は見張りの道具を試験ごとに変え、終わったときだけ起こす
  道具では一度も起きませんでした。直したのはコマンドです(`task events --next` は次の出来事を出して終わり、続きの
  位置を示す)。どの道具でも動く形にします。
- **「黙っていて」より「そもそも届けない」。** 不要な出来事で起きて「報告不要です」と書くのは、`--only` で届く出来事を
  絞るとなくなりました。
- **スキルが約束することを、CLI が本当に出すかを確かめます。** `/chief` が読むはずの replanner のコメントを、
  `task show` は表示していませんでした。
- **herdr のペインを閉じると、0.5 秒ほどで前面のプロセスはすべて消えます。** SIGHUP のあと約 0.28 秒で SIGTERM が届き、
  捕まえても約 0.55 秒後には消えます(実測)。後片づけはその間に終わる分だけにします。自分のセッションで動く子には
  何も届かず残るので、止めるのは親の仕事です。
- **herdr の外から `herdr pane current` を呼ぶと、フォーカスのあるペインが返ります。** 呼んだ場所は、herdr がペインに
  設定する `HERDR_WORKSPACE_ID` で知ります(Claude Code と pi で確認)。id は再起動で使い回されるので、名前も確かめます。
- **タスクは、単独でレビュー・マージ・取り消しができる 1 つの関心ごとにします。** 性質の違う 4 つの作業を 1 枚にすると
  (jyoka/tasks#48)、どれか 1 つの指摘で全部のマージが止まりました。基準を書くと、`/chief` は 5 回中 5 回同じ分け方を
  しました。ただし、小さな作業をまとめるか分けるかは揺れ、分けたタスクの共通の接頭辞は提案だけの試験では付きませんでした。

## 前後関係と、task new 以外の入口 (2026-09-27)

- **誰が、いつ読むかで、書き方が決まります。** 前後関係を Issue の本文に文章で書くだけでは足りませんでした。開始を
  決めるのはコード(`task`)で、エージェントが本文を読むのは開始した後だからです。判断する者が読める形(GitHub の
  「Blocked by」)で持ち、コードで判定します。コードで判定できない条件だけを、エージェントと `/chief` が読む
  Ready conditions に書きます。
- **「一度止めてから立て直す」より「始めない」。** 開始してから Blocked にして replan する案は、枠とトークンを使い、
  エージェントが前提の不足に気づくことに頼り、再実行は前提が入る前のブランチで続きます。前提の PR が未マージで
  止まった過去の Blocked(上記の 2 件の片方)は、始めないことで防げます。本物の aica のタスクでは、#56 と #58 が
  Ready のまま #55 の In review を待ち、マージの後に自動で始まりました。
- **設計の案は、失敗の形を 1 つずつ問うと穴が出ます。** 「もう一度レビュー」で、待ち先が不要として閉じられた場合、
  待っているカードが実行の枠を使う、待ち先が止まったまま何も表示されずに永久に待つ、の 3 つが見つかりました。
  「前提が来なかったら」「来たけれど中身がなかったら」「誰がそれに気づくか」を問います。
- **入口が 1 つだという暗黙の前提は、ほかの道具が来た日に壊れます。** 登録は `task new` を通るはず、という前提で、
  頼んだ workspace の記録も前後関係も `task new` の中だけにありました。to-issues が `gh issue create` で 12 件を
  作った日に、タブが専用の workspace に開き、前後関係は本文の文章にしか残りませんでした。直し方は、入口を縛ることでは
  なく、入口によらず正しく動くことです。タスクの情報は GitHub の標準の形(リンク、ラベル、カードの欄)に置き、
  手元の情報(workspace)は人が開始した時と場所で記録し、本文の文章は開始を止めるためにだけ使います(許可には
  使いません)。安全網は、実物の 12 件で本文の番号と手で付けたリンクが一致することを確かめてから入れました。
- **他人のスキルは書き換えず、入口に 1 行足して、自分の側に安全網を持ちます。** to-issues はコピーで入れたスキルなので、
  更新で上書きされます。手順は task-hub の [issue-tracker.md](issue-tracker.md) に置き、スキルにはそれを読む 1 行だけを
  足しました。その 1 行が消えても、上の安全網で並行には始まりません。
- **ユーザーに渡すコマンドは、ユーザーのシェルで動くかを確かめます。** 自分の環境で動いた書き方を渡したところ、zsh は
  変数を単語に分けないので、16 本のリンクのうち 11 本が作られませんでした。失敗した行は書き込み前に止まったので
  実害はなく、1 行に 1 組の形で渡し直しました。
- **本物での試験は、後片付けのいらない形にします。** 前後関係の E2E は調べもののタスク 2 件で行い、PR を作らずに済み
  ました。満たされない Ready conditions をわざと入れておくと、エージェントがその条件を名指しして、何も変えずに止まる
  ことも同じ試験で確かめられました。

## エージェントごとの違い (2026-09-27)

- **同じスキルフォルダでも、呼び方はエージェントごとに違いました。** Pi で `/chief` が出てこなかったのは、入れ忘れでは
  なく呼び方の違いでした(Claude Code と Kiro は `/chief`、Pi は `/skill:chief`、Codex は `$chief`)。ドキュメントには
  Claude Code での呼び方しか書いていませんでした。「どのエージェントでも使える」と書くなら、エージェントごとに公式の
  ドキュメントで確かめ、呼び方まで書きます。
- **共通の仕様の外の設定は、共通ではありません。** 「頼まれたときだけ使う」(`disable-model-invocation`)は Claude Code と
  Pi は読みますが、Codex は読まず(スキルの `agents/openai.yaml` で指定)、Kiro のドキュメントには載っていません。
- **「自分から知らせる」は、エージェントの実行環境の機能に頼っていました。** `/chief` の見張りは、終わったときに
  エージェントを起こすバックグラウンド実行が前提で、Pi にはそれがありません。プロンプトで工夫するのではなく、見張りの
  ループを Pi の拡張機能としてコードで書き、出来事ごとにメッセージを送って起こしました(0.6 の `task events --next` と
  同じく、道具の違いをコードで吸収する形)。本物の Pi を RPC モードで動かし、HOME を分けた出来事のファイルで試したので、
  動いている本物の `/chief` を起こさずに確かめられました。
- **最小の E2E は、エージェントに依る部分だけに絞ります。** 仕事用の Mac で使う Kiro は、Kiro の呼び出し 3 回で確かめ
  ました(実装、初めての Kiro での自動レビュー、Kiro からの `/task`)。git、PR、前後関係はエージェントに依らず、すでに
  確かめてあるので省きました。Kiro のシェルには `task` が PATH になく、スキルに書いておいた
  `~/.local/lib/task-hub/bin/task` への切り替えがそのまま効きました。
- **本物のボードでの試験は、本物の作業とボードを共有しています。** 試験のつもりの `task start 73` が、Ready で待っていた
  別の 2 件(#71、#72)も始めました。`task start` は Ready のカードをすべて始める作りなので正しい動きですが、試験の前に
  `task list` で Ready のカードを確かめます。

## Ready の前の Goldfish を過去のカードで試す (2026-10-27、タスク 252)

`task check`(Goal とコードしか知らない Goldfish の GO / NO-GO。[task-format.md](task-format.md#ready-の前の確かめtask-check))を、
自動レビューに通らなかった過去のカード 5 枚にかけました。問いは「NO-GO の指摘は、実際の不合格の理由と重なるか」です。

**結論: 5 枚とも、実際の不合格の理由は Goal の曖昧さではありませんでした。** blocking の指摘が不合格の理由と重なったのは
0 枚です。minor の指摘が理由の手前(定義が決まっていないこと)に触れたのが 2 枚ありました。不合格の理由は、どれも実装の
端の穴でした(例外の経路、`~` の展開、正規表現の穴、1 つずれ、全角の記号)。この 5 枚では、Ready の前の Goldfish は不合格を
防げず、実装後のレビューの代わりにはなりません。

| カード | 実際の不合格の理由(最後のレビューの Please fix) | 判定 | blocking / minor | 重なり | 時間 | トークン(出力) |
|---|---|---|---|---|---|---|

   指している」「形 B〜D とのつなぎ口をどのタスクが決めるか」です。これらが実際に実行を迷わせたかは、レポートを読んでいないので

4. **Goldfish はリポジトリの外も探しに行く。** 最初の試しで、`find / -maxdepth 6` を数分動かしました。文脈のない読み手に

5. **Readiness の段は、批評の言い過ぎを落とす。** #200 では、Design Critic が blocking とした「方式と関係のない失敗の扱い」を、

- 新しいカードで `[runner] readiness = warn` を動かし、NO-GO のまま始めたカードと GO のカードで、自動レビューの不合格の割合が
  違うかを見る。過去のカードでは、Goal の質と実装の穴が分けられないため。
- 実装の端の穴に効くのは、Goal の確かめより、受け入れ条件に「この入力でこうなる」を書くことかもしれない。NO-GO の指摘に
  「受け入れ条件に足す入力の例」を出させるかを考える(推測)。

2. **agent はレポートを理由に確かめを省いていました。** #238 と #249 の agent は、どちらも「レポートに全部のテストの結果が

3. **視点が違っても、同じ穴を別の言葉で指摘します。** #249 では 2 視点が同じ README の行を、#282 と #238 では同じ minor を
   別の文で出しました。文の一致だけでは 1 つにならないので、指摘の先頭の場所(`` `README.md:46` `` のような `path:line`)が
   同じで視点が違えば、1 つにまとめるようにしました(2 つ目の文は「Also」として残します)。この比べ方を入れる前の試行なので、
   表の数は 2 件と 1 件に分かれたままです。#249 の 3 件は、今のまとめ方では 2 件です。
4. **goldfish は minor が多く、blocking に強めに倒れることがありました。** minor は 1 時点あたり 4〜7 件(agent は 1〜5 件)で、
   重なりを除いても多めです。#249 の誤検出は、agent が minor とした同じ穴を、Codebase Auditor が blocking にしたものでした。
5. **時間は視点の数より延びました。** 視点を 1 体ずつ動かすので、時間は 2 倍を超えました(2.5〜7.8 倍)。各視点が
   レポートの代わりに自分で確かめるので、1 体あたりの時間も長くなります。

既定は `agent` のままにすることを提案します。理由は 3 つです。

- この 4 回では、goldfish が agent の見逃しを見つけた回はありませんでした。
- 誤検出は goldfish にだけ出ました。
- 時間は約 4 倍、token は約 3 倍でした。1 回の実行の中央値(約 21 分、約 560 万 token。design.md の上限の節)に
  レビュー 1 回あたり 10 分以上を足すことになります。

次に確かめることは 3 つあります。

- 同じ時点を各方式で 3 回ずつ動かし、ぶれを見る。1 回ずつでは、#238 の見逃しが方式の差か偶然かを分けられません。
- 見逃しの多い種類(lessons の 252 の節の「実装の端の穴」)に効くかを、元のレビューが不合格にしたほかのカードで見る。
  aica のカードには `[setup]` と `[env]` が要るので、`task review` に `--setup` のような道を足すか、実行の中で試す。
- goldfish を使うなら、カードごとに選べるとよい(例: 変更が大きいカード、レポートの主張が多いカードだけ)。今の設定は
  マシン全体の `[runner] review_mode` だけです(推測。別のカードにする)。

## task-hub のシンプルさのルール

1. このプロジェクトで示されたユーザーのニーズがない機能は作りません。「役に立つかもしれない」では不十分です。
2. 新しいものより、プレーンなファイルと既存のツール (git、gh、herdr、各エージェント自身の CLI) を優先します。
3. 1 つのことをする方法は 1 つだけにします。
4. 実際の実行で問題が見つかったら、最小の箇所で修正し、それを検出できたはずのテストを追加します。

## まだ検証できること

価値の高い順に並べています。それぞれ機能ではなく、1 つの小さな実験です。確かめ終えたら、上の教訓に移すか消します。

1. **実際のリポジトリでの、前後関係のある連続したタスク。** jyoka/tasks #55 から #65(aica v1)が進行中です。
   待っていたタスクは、前のタスクの変更を前提に正しく作業できるでしょうか。レポートとレビュー一覧は、複数ファイルに
   またがる変更でもレビューの時間を節約できるでしょうか。
2. **to-issues からの登録。** 足した 1 行を読んで、`task new --blocked-by` で登録するでしょうか。PRD はボードに
   載せないでしょうか。次に PRD を分けるときに確かめます。
3. **`/chief` の、前後関係のある Done の扱い。** 待っていたタスクを見つけて、Ready なら自動で始まる旨を、Backlog なら
   Ready conditions を読んで開始を提案するでしょうか。スキルの文面を変えただけで、本物ではまだ試していません。
4. **仕事用の Mac。** Kiro での実装、自動レビュー、`/task` は個人の Mac で確かめました(kiro-cli 2.22.1)。会社の GitHub が Enterprise Managed Users の場合、Project を
   作れるか、同僚のマージで `Closes <自分>/tasks#N` が自分の private な Issue を閉じるか、無人の間 `kiro-cli` が
   ログインしたままでいられるかは未確認です。
5. **Codex と Pi での `/task`、Codex と Kiro での `/chief` の見張り。** `/task` は Claude Code と Kiro で確かめました。
   Codex と Kiro が `/chief` をバックグラウンドで起こせない場合、返答のたびに確かめる動きになります。Kiro が
   満たされない Ready conditions で止まるか(Claude では確認済み)も未確認です。
6. **ブロックされてから、解除されるまで。** 途中まで変更して Blocked になり、同じブランチと PR で続ける場合は、まだ
   フェイクのエージェントでしかテストしていません。
7. **前後関係のない、同じファイルに触れる 2 つのタスク。** PR は競合し、task-hub はまだ検知しません。「一方をマージし、
   もう一方を再実行する」で十分でしょうか。
8. **長時間の実行とスリープする Mac。** 2026-10-26 に確かめました。スリープの間、`_run`、エージェント、`task watch` は止まったまま残り、
   起きると続きます。実行は止まった扱いにはなりません。claude は切れた返答を自分で「cut off mid-stream」として再開し、
   起きた直後の DNS のエラーも再試行しました(task 214、40 分の休止)。pi も、10 分止めたあとの「WebSocket error」を
   1 回の再試行で越えました(SIGSTOP でのまね)。`slow` は壁時計で数えるので、スリープの時間も足されます。
   まだ確かめていないのは、本物のふたを閉じたときの pi と、本物の再起動です。人が確かめる手順: 使い捨ての HOME と
   偽の GitHub で偽の遅いエージェントと本物の pi を 1 つずつ動かし、(1) ふたを 10 分閉じて開き、`task log` と `ps` で
   続いたかを見る、(2) 再起動してログインし、`task watch` の最初の同期で `resumed:` が出るかと herdr のタブを見る。
9. **ネットワークが必要なテストを持つ Codex。** デフォルトのサンドボックスのままで、テストは通るでしょうか。
10. **自動レビューの誤検出と見逃し。** 本物のタスクで、`needs changes` はどれくらい正しく、差し戻しで直るでしょうか。
    1 回の実行の中の「needs changes → 差し戻し → pass」は、フェイクでしか確かめていません。
    誤検出は、2026-10-26 に既存の Blocked のレポートから集計しました(タスク 249)。結果は約 9% で、下限と見ます。

    | 数えたもの | 数 |
    |---|---|
    | #129〜#248 の Blocked のレポート(Issue のコメント単位) | 52 |
    | そのうち自動レビューによるもの | 41(28 枚。差し戻し後も不合格 40、`blocked` 判定 1) |
    | blocking の指摘(最後のレビューの `Please fix` の項目) | 67 |
    | 本物 / 誤検出 / 不明 | 60 / 6 / 1 |
    | 誤検出率 | 6 / 66 = 9.1%(不明を除く)、6 / 67 = 9.0%(全部) |
    | 誤検出だけでブロックしたレポート | 41 件中 2 件(#225、#226) |

    数え方は次のとおりです。

    - **対象**: jyoka/tasks の Issue のコメントのうち、`<!-- task-hub report -->` と `## Blocked` があり、理由が
      `automated review` で始まるもの。数えたのは最後のレビューの `Please fix` の項目です。
    - **本物**: 人か総指揮が直すと書いた、次の実行が直して次のレビューが通った、マージした PR に直しが入っている、のどれか。
    - **誤検出**: 人か総指揮が直さないと決めた、直さずにマージした、Goal やそれより前の利用者の決定に反する、のどれか。
    - **不明**: 根拠が足りないもの。推測では埋めていません。

    誤検出の 6 件は、すべて評価用の判定の正規表現の穴を指したものでした(#224、#225、#226)。このうち 5 件は、
    「判定の正規表現は目安で、自動レビューもこの決まりで判定する」という利用者の決まりが Issue に出たあとのレビューでした。
    本番のコードへの指摘に、誤検出は見つかりませんでした。

    率が低めに出る理由が 2 つあります。本物の 60 件のうち 19 件は、根拠が「次の実行が従い、次のレビューが通った」だけです。
    約 20 件は、総指揮の Claude の同意が根拠です。どちらも、指摘が正しいことの独立した証明ではありません。
    #129 より前の 10 件は数えていません。

    多かったのは、誤検出よりも、直すたびに同じ所に別の穴が出る形です(#130、#211、#229、#242)。#242 では、
    人がレビューの直し方をそのまま指示に写して Ready に戻し、その直し方が次の後退を生みました。これを受けて、
    差し戻しの回数を設定できるようにし、進まなくなったら止め、指摘を blocking と minor に分けました
    ([design.md](design.md) の決定事項 32)。見逃し(`pass` のあとに見つかった不具合)は、まだ数えていません。
