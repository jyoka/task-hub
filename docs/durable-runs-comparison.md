# 止まった実行の再開: A・B・C を比べた結果

止まった実行を task-hub が 1 回だけ自動で再開するとき、どのやり方で続けるかを比べた実験の結果です。
設計と決めたことは設計メモ [architecture/designs/durable-runs.md](architecture/designs/durable-runs.md) にあります。
本採用は人が決めます。この文書は案を出すだけです。

| 方式 | 続け方 |
|---|---|
| A | エージェントの CLI が保存した会話を使う。pi の `--session-id {session}` で、初回も再開も同じ会話 |
| B | Pi Durable の実行役(`durable/`)。会話と途中のツールの呼び出しを SQLite に残し、`harness.resume()` で続ける |
| C | 新しいセッションで最初から。プロンプトに「# Resumed」の節が付くだけ |

## 本採用の案

**決めたこと 10 の順を字面どおりに当てると、B が先に立ちます。** 1 は同点で、2 と 3(トークン)で B が先に立つためです。
この文書の案は、その順から外れて **A を条件つきで勧めます**。条件は、A でも前の起動のツールのコマンドを止める作りが入り、
それが確かめられることです。条件が満たせなければ、順のとおり B です。C は、会話の ID を渡せないエージェント(codex、kiro)の
再開として、どちらの場合も今のまま残ります。

決めたこと 10 の順に見た結果です。

1. **最終結果がテストに通る割合**: 3 方式とも 21 回中 21 回で、差はありません。ただし B は、落とした 2 回で
   「1 回だけ動かす」リリースノートのスクリプトを動かさずに終えました。Goal を全部終えた回数は A 21、B 19、C 21 です。
   この 2 回のうち B-T2-K2-2 は、同時に動いていたほかの試行の pytest と、実験台が残した `.running` を見て止まりました。
   B の弱さを測った数ではなく、実験台の影響の恐れがあります(「分かったこと」)
2. **副作用の二重の実行**: B が先に立ちます。リリースノートが 2 回動いた試行は、どの方式にもありません。
   設計メモの「測るもの」は、長いテストの回数(数えるファイルの行数)でも測ります
   - 長いテストの余分な回数: A 9、B 4、C 12
   - 長いテストが 2 つ同時に動いた試行: A 1、B 0、C 4。どれも長いテストの途中で落とした試行(T2 の K1 と K2、方式ごとに 4 回)で起きました

   A と C の差は、前の起動のテストが残っているかをモデルが確かめたかどうかです。B が 0 回なのは、実行役が続ける前に
   残ったコマンドを止めるためです(`durable/scripts/group-shell`)
3. **やり直した量**: トークンでは B が先に立ちます。落とさない試行との差の中央値は次のとおりです
   - トークン: A +38k、B +8k、C +13k
   - ツールの呼び出し: A +1.5、B +2、C +11.5
   - 時間はどれも +0.1〜0.2 分

   C は調べ直しが多く、A は会話全体にプロンプトを足して送り直すのでトークンが増えます
4. **保守の重さ**: A が先に立ち、差がいちばん大きい基準です
   - A: `bin/task` の +67/-25 行だけで、依存は増えません
   - B: `durable/` の `src/` と `scripts/` で 537 行、テストで 327 行が増えます。固定した依存は 4 つ(lockfile では 122 パッケージ、`node_modules` は 157 MB)です。
     実験版で「API は予告なく変わる」パッケージの名前を約 20 使い、モデルは `openai-codex` だけ、Node 22.19 以上が要ります

### 順から外れて A を勧める理由と、頼っている前提

A を勧めるのは、2 と 3 の B の利点が A にも移せるか、小さいと見るためです。どちらも確かめていない前提に頼っています。

- **(a) B の止め方は A にも足せる(推測)。** B の止め方は、pi-durable の `NodeExecutionEnv` の `shellPath` に
  `group-shell` を差し込んで成り立っています(`durable/src/runner.ts`)。pi 1.4.0 の CLI にも `settings.json` の
  `shellPath` の設定があり、`bash` のツールがそれを使います(pi-coding-agent の `settings-manager.js`、`tools/bash.js`)。
  このため A でも同じ差し込みができると推測します。ただし、次のことは確かめていません
  - task-hub から pi の `shellPath` を、利用者の設定を変えずに渡せるか
  - claude の CLI に同じ差し込み口があるか
  - 起動するときに pid を記録する作り(「後のタスクの案」)では、あとから生まれるコマンドのグループは記録できない。差し込み口がないエージェントでは、別の作りが要る
- **(b) A の増えたトークンは、上限への響きが小さい(不明)。** A の増えた分の多くはキャッシュから読んだ入力です
  (A の 2.0M のうち 1.7M)。ただし、キャッシュから読んだトークンが ChatGPT のサブスクリプションの上限にどう数えられるかは
  不明です(「確かめていないこと、限界」)。このため、3 のトークンの差を打ち消す根拠にはなりません

そのほかに A を推す点は 2 つです。

- 4 の保守の差がいちばん大きいこと。これは数えた行数と依存で、実験台の影響を受けません
- B は Goal を終えないまま終わった回が 2 回あること。**この根拠は弱まりました。** 2 回のうち B-T2-K2-2 は、ほかの試行の
  pytest と、実験台が残した `.running` を見て待ち、リリースノートを動かさずに終えました。もう 1 回の B-T2-K1-1 は、
  成果物のフォルダが残っておらず、何を見て止まったかを確かめられません。このため「B は Goal を 2 回終えなかった」は
  計測ではなく、実験台の影響の恐れがあるものとして扱います。T2 を 1 つずつ動かし直せば確かめられます(「T2 を 1 つずつ動かし直すなら」)

A を推す根拠で確かなのは、4 の保守の差だけです。試行の数が少ない(1 つのマスに 2 回)ので、2 と 3 の小さな差は偶然の範囲かもしれません(推測)。
(a) が成り立たないと分かったら、A の案は取り下げ、順のとおり B を案にします。

**決めてほしいこと**: 本採用を次の 2 つのどちらにするか。

- **A(条件つき)**: 保守の軽さを取る。(a) を確かめるタスクを先に入れ、だめなら B に切り替える
- **B**: 決めたこと 10 の順のとおり。2 と 3 で先に立ち、Goal を終えなかった 2 回は実験台の影響の恐れがあるとみる

## 課題と落とし方

### 課題

実験のスクリプトが、試行ごとに小さな Python のリポジトリを作ります(`tests/durable_bench.py` の `project`)。

- `calc/stats.py` に 3 つ、`calc/text.py` に 1 つのバグがあり、テストが落ちる
- `tests/test_slow.py` は約 20 秒かかる。始まると worktree の外の数えるファイルに 1 行足し、走っている間 `.running` を置く
- `scripts/add_changelog.py` は CHANGELOG に 1 行足す。動かすたびに足すので、2 回動かすと壊れる。動くたびに数えるファイルにも 1 行足す
- 全部のテストが通ると `conftest.py` が `.tests-passed` を置く

Goal は「テストを通す。テストは変えない。全部が通ったら `add_changelog.py` を 1 回だけ動かす。レポートを書く」です
(`GOAL`)。答えは、push したブランチに元のテストを戻して pytest で確かめます。

### 落とし方

| タイミング | 合図 |
|---|---|
| T1 モデルの返答の途中 | ログに最初のツールの呼び出しの行が出てから 2 秒後 |
| T2 bash の実行中 | `.running` があるとき(長いテストの途中) |
| T3 ファイルを書いた直後 | `calc/stats.py` の中身が初めて変わったとき |
| T4 レポートを書く前 | `.tests-passed` が現れたとき |

| 止め方 | すること |
|---|---|
| K1 | エージェントのプロセスグループだけを kill -9。`_run` がその場で再開する |
| K2 | `_run` とエージェントを kill -9 し、すぐ `task`(同期)を 1 回動かす。`relaunch` で再開する |
| K3 | 再起動のまね。使い捨ての HOME で動くもの(`task watch`、`_run`、エージェント、ツールのコマンド)を全部 kill -9 し、`task watch` を起動し直す。T2 だけ |

方式ごとに、落とさない 3 回、T1〜T4 × K1、K2 を 2 回ずつ(16 回)、T2 × K3 を 2 回で 21 回です。全体で 63 回になります。
54 回の落とす試行は、どれも合図が来てから落とせました(`missed` は 0)。

「落ちた所」は、落とした時刻の直前の会話から分けました。直前が user かツールの結果ならモデルの返答の途中、
ツールの呼び出しなら、ツールの実行中です。T1 の 12 回と T3 の 12 回は、すべてモデルの返答の途中でした。
T2 はすべてツールの実行中です。T4 は両方ありました(pytest が `.tests-passed` を置いてから終わるまでの間に落ちた回がツールになる)。

```sh

python3 tests/durable_bench.py --list                      # 63 回の試行の名前と、済んだかどうか

```

- 使い捨ての HOME、偽の GitHub(`tests/test_task.py` の `FAKE_GH`)、手元の bare リポジトリで動かします。本物の設定、

- テストではありません(名前が `test_` で始まらない)。ChatGPT のサブスクリプションを使うので、頼まれたときだけ動かします

## 分かったこと

### B は、切られたテストをやり直さずに止まることがある

B-T2-K1-1 と B-T2-K2-2 では、再開した B がリリースノートを動かさずに終えました。どちらも長いテストの途中で落とした回です。
ただし、少なくとも B-T2-K2-2 は実験台の影響を受けています。B の性質として測れたとは言えません。

B-T2-K2-2 で起きたことです(`task.log` と SQLite で確かめた)。

- 実行役は、続ける前に残ったテストのプロセスグループを止め(`stopped process group 16376`)、モデルには「その bash は interrupted」と渡しました
- モデルは `ps -Ao pid,ppid,etime,command | grep pytest` で、マシンの全部のプロセスを見ました。そこに出た pytest は、自分のものではありません。
  同時に動いていたほかの試行の pytest と、実験のスクリプトが答えを確かめる `pytest -q -p no:cacheprovider` です。
  自分の長いテスト(数えるファイルの `start 16382`)は、実行役がもう止めていました
- `.running`(07:35 の時刻)も残っていました。実行役は SIGKILL で止めるので、テストの `finally` が動かず、`.running` が残ります。
  実験台の作りによるものです。A と C の K1、K2 では前の起動のテストが最後まで走って消すので、たいていこうなりません
- モデルは `sleep 22`、`sleep 25` で待ち、pytest が見えたままなので全部のテストを走らせ直さずに、
  「The full suite was interrupted ... so I did not run the changelog script」と書いて終えました
- 答えは正直ですが、Goal は終わっていません。カードは In review になります(task-hub はレポートの中身で Blocked にしない)

B-T2-K1-1 は成果物のフォルダが残っておらず、何を見て待ったかを確かめられません(「確かめていないこと、限界」)。

B の作りのほうに理由がある、という推測もあります。B は task-hub の「# Resumed」の節を送らない作りです(会話をそのまま続けるため)。
一方で worker のプロンプトには「時間切れのコマンドを、原因を直さずに同じまま走らせ直さない」とあります。
A と C は「# Resumed」で、何が止まったかと、続け方(`git status` を見る、2 回走らせてまずいものは終わったかを確かめる)を受け取ります。
A にも、テストの結果が分からないまま、リリースノートを動かした回が 1 回ありました(A-T2-K1-2。最終結果は正しい)。

### 長いテストが同時に 2 つ動くのは、前の起動のツールのコマンドが残るため

pi 1.4.0 の `bash` は、コマンドを自分のプロセスグループで動かします(lld.md 7 章)。K1 と K2 でエージェントの
グループを止めても長いテストは残り、最後まで走ります。

- C は前の会話を知らないので、残ったテストに気づかず、もう 1 つ走らせました(T2 の K1、K2 で 4 回中 4 回)
- A は会話を覚えているので、たいてい `ps` で残ったテストを見つけて待ちました(4 回中 3 回)。ただし `ps` には、同時に動いていたほかの試行のプロセスも見えていました。B も同じです(「確かめていないこと、限界」)
- K3 はすべてを止めるので、どの方式でも同時には動きませんでした

worktree の外に書く長いコマンドが 2 つ同時に動くと、結果が混ざります。この課題では壊れませんでしたが、仕組みでは
防げていません。

### やり直した量

- A は再開のたびに、元のプロンプト全体と「# Resumed」を、前の会話の後ろに足して送ります。そのあとの各ターンも
  その長い会話を送るので、トークンが増えます。A の 2.0M のうち 1.7M はキャッシュから読んだ入力です
- C は前の会話がないので、ファイルを読み直し、テストを走らせ直します。トークンは A より少なく、ツールの呼び出しが多くなります
- B は送り直しがなく、余分がいちばん少なくなりました。T2 と K3 だけ、待つ、確かめる、で増えます

## 確かめていないこと、限界

- 試行の数が少なく(1 つのマスに 2 回)、課題も 1 つで短いです。長い課題や、ほかのモデル、claude での比べはしていません
- 本物の再起動とスリープはしていません。K3 は、使い捨ての HOME の中で動くものを kill -9 するまねです

- 落とした瞬間に作っていた返答のトークンは、どの方式も数えていません。pi の会話のファイルにも、B の SQLite にも残らないためです。やり直した量は少しだけ小さく出ます
- 同じ落とし方の A、B、C を 3 つ同時に動かしました(`-j 3`、`trials()` の並び)。エージェントがマシンの全部のプロセスを見ると、ほかの試行の pytest や B の実行役も見えます
  - 全部のプロセスを見る `ps`(`ps -axo`、`ps -Ao`、`ps aux`)は、成果物の残る 60 回のうち 12 回のログにあります。

## 後のタスクの案

本採用を決めたあとに、人が登録します。

- **A と C で、前の起動のツールのコマンドを止める。** B の `group-shell` と同じことを task-hub 側で行う。pi なら、
  `bash` のツールの `shellPath` に `group-shell` のようなものを差し込み、再開の前に残ったグループを止める案がある
  (使えるかは確かめていない。「本採用の案」の (a))。起動するときに pid を記録するだけでは、あとから生まれる
  コマンドのグループは拾えない。長いテストが同時に 2 つ動くのを、モデルの判断ではなく仕組みで防ぐため。
  A の案はこれが確かめられることが条件
- **A の再開のプロンプトを短くする。** 会話が残っているときは、元のプロンプト全体ではなく「# Resumed」の節だけを送る。
  会話のファイルが消えていたときの扱い(設計メモ「失敗したとき」)を先に確かめる
- **B を採らないなら、`durable/` を消すか、`rust/` のように実験として残すかを決める**(決めたこと 6)。消すなら、
  CI の手順、`tests/test_task.py` の `test_durable_runner_*`、agents.md の 1 行、HLD と LLD の行も消す
- 本物の再起動とスリープでの再開を、人が 1 回確かめる
